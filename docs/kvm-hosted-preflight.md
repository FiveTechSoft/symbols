# Hosted Linux KVM preflight

This is an exploratory capability measurement, not a sandbox accreditation and not permission to run workspace C in a VM. It measures a particular `ubuntu-24.04` hosted job at the time it runs. The probe imports only Python's standard library. The workflow uses a commit-pinned raw script and SHA-256 check, no checkout, secrets, repository source, network device, disk, host share, or target-code compile/run. The only VM payload is a script-built cpio initramfs with a distro `busybox-static` binary and a fixed marker `/init` script. The kernel and QEMU come from the runner's Ubuntu packages. The workflow author should verify the package versions and independently judge the kernel's trust before any future use for untrusted code.

Run on a standard x86-64 Ubuntu 24.04 hosted runner with `qemu-system-x86`, `busybox-static` and a bootable Ubuntu `linux-image-generic` kernel image present. Example after installing those packages: `python3 tools/kvm_preflight/probe.py --kernel /boot/vmlinuz-<installed-generic-version> --busybox /bin/busybox --qemu /usr/bin/qemu-system-x86_64 --json-out preflight.json`. Host absolute deadline belongs to the workflow (`timeout-minutes` and shell `timeout`); the script has a 20-second monotonic deadline per boot and 2+3 seconds to terminate/reap the process group. The host workflow must set a job timeout; do not trust the script as a complete isolation boundary.

The JSON is one line, with `schema`, `classification`, `status` (`pass`/`fail`), `environment`, `phases` (`phase`, `pass`, `error`), `boot_attempts` (`boot_ms`, `kill_ms`, `pass`), `p50_boot_ms`, and `error` (`phase`, `code`). `p50_boot_ms` is the middle measured boot time of three successful marker+kill+reap attempts, not launch-to-process-start. It remains null on any failure. `environment` records exact SHA-256 of QEMU, kernel, BusyBox and built initramfs, package ownership and version (or an explicit lookup error), QEMU version, runner image, and KVM API version. Save the JSON from the job before treating a failure as no KVM: the failed phase distinguishes missing device, permission, VM creation, kernel boot and timeout. No generated stdout from the guest is logged.

The script requires `/dev/kvm` O_RDWR, KVM API version 12, then creates and closes a VM FD with `KVM_CREATE_VM`. It launches QEMU with `-accel kvm`; never falls back to TCG. A passing result does not show safe isolation or portability, and does not turn on the Slice B backend. The next security gate must independently assess isolation, filesystem and network boundaries, seccomp/cgroups, C compiler supply, build/run containment, timeout and cleanup, and adversarial tests. This preflight does not assert any of those.

References: [KVM ioctl API](https://docs.kernel.org/virt/kvm/api.html), [QEMU microvm boot model](https://www.qemu.org/docs/master/system/i386/microvm.html), [GitHub-hosted acceleration statement](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/).
