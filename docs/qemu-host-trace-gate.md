# QEMU host trace gate: fixed boot acceptance criteria before boot

Status: design and offline parser only. This patch does not launch QEMU and cannot set `runtime_complete:true`. The static 49-file ELF inventory from the prior gate is an input, not a runtime pin. The first target is a disposable, secret-free Ubuntu 24.04 GitHub runner with effective KVM permission; the server's installed QEMU `.16` is a different input and must not reuse the `.18` closure. TCG would be a distinct measured mode with a separate fixed argv, accelerator module closure and no silent KVM fallback.

## Trace plan

Before any boot dispatch, freeze the exact tracing command, `strace` executable/package digest, execution image/runner provenance, QEMU binary and kernel/initramfs bytes, loader/environment, fixed QEMU argv, and the source snapshot. Use one child-process trace from first `execve` through clean exit, without late attach. `strace -f -qq -e trace=execve,open,openat,openat2 -s 4096` is a proposed starting observation, not yet a claim that all file dependencies are covered. A separate file-syscall inventory must include `openat2`, `statx`, `newfstatat`, `readlinkat`, `access`, relative dirfds and missing probes or prove why a specific call is irrelevant. Any incomplete, truncated, unparsable or unbounded trace refuses. Test whether QEMU loads accelerator `.so`, firmware/ROM, keymap/data, NSS and loader cache paths. No `sudo` QEMU, secrets, network device, writable share or target-controlled C. Trace collection has explicit wall/output/process limits and cleanup; a marker alone is not success.

The current `trace.py` is a **restricted offline pilot**: it parses only an exact subset of open/exec/exit lines, refuses other lines, ensures observed successful files come from the staging root and match the rootfs inventory bytes, requires every static ELF file to have been observed, and produces `runtime_complete:false`. It does not run or orchestrate `strace`; no output from this pilot can accredit a complete runtime. Its test vectors exercise missing files, hostile/relative paths, partial lines, wrong exit, outside-root reads, SHA drift and an unseen static dependency.

## Future boot gate acceptance, not met by this patch

1. Reproduce fixed kernel, minimal initramfs and QEMU package/ELF closure from authenticated snapshot bytes. Check loader, `dlopen` modules and all effective host-opened firmware/data files against a closed runtime inventory on the host; no ambient file, ambiguous resolution, `/etc/ld.so.cache` fallback or path race. The boot must use the same measured files that were traced, not just matching path names after the fact. An unknown file or unsupported tracing syscall is a blocker, not an ignored event.
2. Commit a fixed KVM command line with no dynamic text except immutable staged file paths: `-M microvm -accel kvm -cpu host -m 128M -smp 1 -kernel <kernel> -initrd <initrd> -append 'console=ttyS0 rdinit=/init panic=1' -nodefaults -no-user-config -nographic -serial stdio -monitor none -net none -no-reboot`. Test real effective `/dev/kvm` access, not a kvm-ok banner. Keep the server TCG command separate and measured if used.
3. Run one fixed boot. Demand the sole `SYMBOLS_BOOT_ONLY_SUPERVISOR_READY_v1` serial marker, self-shutdown and QEMU exit 0 within a finite deadline, bounded output and complete process cleanup. Marker without shutdown, timeout, extra/unknown file open or drift fails. Only after the actual trace and independent host file remeasurement can a separately reviewed gate consider `runtime_complete:true` for that mode and host.

A successful boot would prove only this functional boot path. It is **not** accredited isolation, does not run target C and does not enable Slice B; the adversarial VM security gate remains separate.

## Runner collection proposal (diagnostic, fail closed)

`qemu-runtime-collection.yml` is a separate manual, immutable-commit workflow, not a new CI boot or a launch-eligibility signal. Its three required dispatch values are the 40-hex reviewed commit, SHA-256 of that hosted image's `/usr/bin/strace`, and exact `ImageVersion`. Acquire/review the latter two in a **separate no-boot preflight**; do not guess them from another image or convert a binary observed during this run into advance approval. The workflow checks these before any boot and refuses a changed image or tracer. It then builds the frozen Noble archive from verified snapshot metadata, rechecks archive/manifest/static-closure digests, stages selected snapshot files, makes the fixed minimal initramfs, and opens `/dev/kvm` effectively without privilege escalation. No server `.16` or TCG fallback, no C source, guest network, disk or share. The static closure is a selection seed, not proof that it is exhaustive.

The fixed direct loader command uses `--inhibit-cache` and staged library paths; QEMU gets fixed microvm/KVM argv, fixed snapshot kernel and boot-only initramfs, `-L` staged data, and a minimal environment. Trace starts at loader `execve` with `strace -f -qq -s 65535 -e trace=%file,execve`, bounded to 60 seconds, 16 MiB trace and 64 KiB per output; failure or timeout kills the process group. The marker exactly once (CRLF or LF from serial; bounded kernel messages may surround it), clean exit, and complete log are necessary but not sufficient. The run-local report lists observed successful opens, missing/metadata probes, ambient paths, unsupported syntax count/line numbers, file hashes, absent static files, binary/kernel/initramfs/tracer bytes, exact argv, image identifier and trace hash. Raw serial and raw trace remain run-local and are not uploaded. A one-day report artifact is uploaded even when collection fails. A blocked report exits nonzero by design; a red run with a report is useful measurement, not a host-closure pass.

This collector **never** sets `runtime_complete:true`. A success-looking boot still blocks on ambient cache/NSS/firmware/module paths, unresolved syscall/dirfd/symlink semantics, possible path replacement races and incomplete proof about file-backed mappings. A later gate must explicitly enumerate all file syscalls on the pinned strace version, resolve dirfd/cwd and unsuccessful probes with a closed allowlist, account for kernel-mapped PT_INTERP, prove file identity at use time (not just post-read pathname), and review any required additions to the signed snapshot inventory. This diagnostic cannot promote the 49-file static set on its own. Do not run until exact runner/tracer values and the patch bytes pass review.

## No-boot tracer preflight proposal

`.github/workflows/qemu-strace-preflight.yml` is a manual Ubuntu 24.04 runner measurement. It accepts an exact reviewed commit equal to the workflow's dispatch `GITHUB_SHA` on master. It does not check out a repository, open KVM, launch QEMU or run any guest. It installs `strace` in the disposable job and writes a bounded JSON report: ImageVersion/ImageOS, exact `/usr/bin/strace` SHA-256/size, installed package version/architecture and reported tracer version. No inference from an unpinned apt version to a permanent binary pin. It uploads only the report for one day; failure to acquire/measure or mismatch returns a blocked classification and a red job.

Initial measurement leaves both expected fields empty and reports `measured_only`, **not** launch approval. A later verification takes BOTH ImageVersion and SHA-256 supplied after independent review; a mismatch blocks. A matching pair is only a comparison, not proof that the values were actually reviewed. Inputs are values for comparison, not proof of their own review. The QEMU collection workflow also requires those two values, checks the runner image before boot and independently rehashes the tracer. Hosted image version equality alone does not prove the full runner image is immutable or supply-chain verified. No workflow auto-dispatches collection from this report. The reviewer must decide whether the observed pair and package provenance are adequate, then dispatch separately; later runtime-closure and isolation gates remain open.

## Runner KVM group diagnostic continuation

The first two collection dispatches blocked before QEMU: #1 at a valid snapshot data filename with a comma (fixed through a separate CI gate), #2 because the runner process lacked effective `/dev/kvm` access. The group continuation proposes `sudo usermod -aG kvm runner` in a preparatory step only, then `sg kvm -c` to start the collector unprivileged in a new process with active kvm GID. It requires the device's GID to equal the `kvm` group GID, the current user and effective UID non-root, the active group set to include that GID, group read/write mode, and a successful O_RDWR open. It records UID/EUID/EGID, active GIDs and device group/mode in the diagnostic JSON before the boot. If any check fails it blocks; no `sudo` QEMU, permissive device chmod or TCG fallback. This is a runner-specific capability path, not host-closure or isolation accreditation. An ImageVersion/strace mismatch remains a preboot failure. A successful KVM open is not evidence of complete host file-open coverage.

## Bounded stderr categories and trace PID prefix after collection #5

Run #5 passed the staged loader-only dependency check but the traced launch returned 1 without a serial marker. It wrote 48 stderr bytes that were not in the previous whitelist, so the exact cause remains unknown. This patch adds fixed failure categories for common QEMU kernel, initrd, firmware, KVM, accelerator and generic file-open errors. It emits no free-form error lines, user paths or raw guest bytes. A message outside the whitelist stays `unclassified`; a matching phrase is diagnostic, not proof of its cause. The independent trace parser fix accepts `strace -f -qq -o` decimal PID prefixes of at most 12 digits, as well as the existing `[pid N]` form; all other unsupported lines continue to block. A local strace 5.16 sample gave numbered lines and retained unsupported calls after this fix. The runner uses pinned 6.8 and must be measured again: no missing opens or unsupported coverage can be inferred from the earlier 93/93 unparsed trace. Neither change promotes `runtime_complete` or closes host/isolation proof.

## Structured diagnostic shapes after collection #6

The sixth hosted collection repeated the same 48-byte stderr digest and exit 1 without a serial marker. A wider fixed-category match still left it `unclassified`. The trace had 97 unsupported lines and no accepted opens, so the prior PID-prefix hypothesis did not explain it. To diagnose without publishing guest output or raw trace, this gate adds a 256-byte ceiling on stderr word analysis: a fixed public word lexicon is the only output vocabulary; every path, token containing digits, unknown word, or control character is redacted/suppressed. The original size/hash/categories remain. Trace shape counts and at most eight unsupported-line samples contain only PID-prefix class, known syscall name or `other`, structural delimiters and line number, never argument values or raw lines. This is a diagnostic report, not coverage: unsupported syntax and unknown ambient files remain blockers, and `runtime_complete` stays false.

## Measured double-space PID and candidate BIOS name after collection #8

The eighth diagnostic run reported that `strace 6.8` lines begin with a decimal PID followed by exactly two spaces before recognized `execve`, `openat`, `access` and `newfstatat` names. The prior parser matched only one. This patch accepts one or two ASCII spaces after a bounded decimal PID in the conservative diagnostic parser and exec probe; tabs and three spaces still refuse. ## Relative successful open after collection #12

Run #12 again booted but traced an unsupported successful `openat(AT_FDCWD, relative pathname)` with a short unescaped name. The actual name and object are not established by its shape. This patch adds post-run diagnosis, not parser acceptance. The launch cwd is the staged root; any traced `chdir`/`fchdir` makes cwd-based resolution blocked. Linux `openat2` against the stage directory fd uses `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS` and rejects path traversal, missing paths, and symlinks. `fstat` identifies only regular/directory/other. A bounded regular file is reopened with the same resolution rules, compared by device/inode/size to the first fd, then hashed; only an exact inventory member may be named in the report. Non-inventory members emit no name, just state/kind/hash when safely measurable. Failed or ambiguous resolution stays blocked. This is a read after QEMU's open, not immutable open-time identity: an attacker or concurrent change could replace contents in between. Signal lines are classified structurally, while all unknown paths and the eight ambient successful opens remain blockers. No change to boot args, trace parser acceptance or `runtime_complete:false`.

## Component shapes after collection #13

The post-run diagnostic for the successful relative `openat` in run #13 returned `path_unsafe`; the earlier shape was short and unescaped, but that state combines a harmless-looking `./` prefix with forbidden `..`, empty or repeated separator components. This patch emits only five fixed booleans: leading `./`, any `.`, any `..`, an empty component, and absolute pathname. It strips exactly one leading `./` only when the remainder is nonempty, bounded, relative and has no empty, `.` or `..` component. The existing stage-fd `openat2` no-symlink, no-magiclink, beneath-root resolution and post-run fstat/hash then apply to the normalized name. Any other component shape remains blocked. No raw arbitrary name or signal payload is emitted; this is not open-time identity, parser acceptance, or host closure.

## Dot-component follow-up after collection #14

Run #14 reported an unsupported successful relative `openat` with a `.` component, no leading `./`, no `..`, no empty component and no absolute path. This patch permits post-run diagnosis of exactly this shape: within a bounded relative name, remove all `.` components, preserve every other segment in order, and reject any `..`, empty segment, absolute form, or all-dot result. The same stage-dirfd `openat2` no-symlink/beneath check, fstat, bounded hash and public-inventory-only naming still apply. Neither the unsupported trace line nor the ambient paths become accepted coverage. The result remains a post-run observation, not proof of the object at QEMU open time.

## Literal cwd probe after collection #15

Run #15 still marked the successful relative `openat` path unsafe after dot-component normalization. Its closed flags were relative, a dot component, no leading `./`, no empty component and no `..`; within the bounded shape this narrows to literal `.`. This patch recognizes only that exact first quoted operand for `openat(AT_FDCWD, ...)` or `access(...)` and reports whether the return is successful FD, ENOENT or other. It checks the fixed launch cwd stage fd with `fstat` for a directory and blocks the assertion if a traced cwd change exists. It never emits any arbitrary path, other argument, flag or PID. This is diagnostic only: the `openat` line stays unsupported, host opens and relative access probes still block full closure, and an after-the-fact stage check is not open-time identity.
